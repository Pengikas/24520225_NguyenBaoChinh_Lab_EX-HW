## 3. Defect 1: Cross-Site Scripting (XSS) Vulnerability via Naive Virtual DOM Text Rendering

### 3.1. Defect Description
In early code generated by the AI for `mini_react.js` (`createElement` and `renderToDOM`), child text nodes and string props were processed by creating container elements and assigning `innerHTML = child` or injecting raw HTML strings:
- **Vulnerability:** When dynamic user input (such as a task title entered by a user) contained HTML markup (such as `<script>alert(1)</script>` or `<img src=x onerror="alert('XSS')">`), the browser engine parsed and executed the markup as executable DOM elements.
- **Severity & Impact:** **Critical (CWE-79 / Stored & DOM-based XSS)**. An attacker could execute arbitrary JavaScript within the application context, extract local tokens, or manipulate application state.

### 3.2. Diagnostic Method
1. **Automated Security Checkpoint Verification (`test_runner.js`)**:
   A synthetic virtual DOM tree with malicious script payloads was injected into the test suite:
   ```javascript
   const vApp = createElement('main', { id: 'root-view', role: 'main' },
     createElement('header', { className: 'hero' },
       createElement('h1', null, 'Mini React Engine'),
       createElement('p', null, '<img onerror=alert(1)> Safe Text')
     ),
     createElement('section', { id: 'security-test' }, '<script>alert(1)</script>'),
     createElement('button', { onClick: () => console.log('Ping') }, 'Click')
   );

   const root = document.getElementById('app');
   root.replaceChildren(renderToDOM(vApp));

   // Security Assertions
   console.assert(root.querySelector('button') !== null, 'Mount Failed');
   console.assert(root.querySelector('script') === null, 'XSS Vulnerability: <script> was parsed into DOM!');
   console.assert(
     root.querySelector('#security-test').textContent === '<script>alert(1)</script>',
     'XSS text node verification failed'
   );
   ```
2. **Chrome DevTools DOM & Breakpoint Inspection**:
   - Placed a breakpoint in `renderToDOM(vnode)` at the child mounting loop.
   - Inspected the Chrome DevTools Elements panel: observed that `<script>` and `<img>` nodes were actively mounted when using the AI naive implementation.
3. **Git Diff Inspection (`git diff e5c3221 c5075cb`)**:
   Audited the transition from raw element creation to normalized `createTextElement`.

export function createTextElement(value) {
  return {
    type: "TEXT_ELEMENT",
    props: { nodeValue: String(value) },
    children: []
  };
}

export function createElement(type, props, ...children) {
  return {
    type,
    props: props || {},
    children: children.flat().map(child =>
      typeof child === "string" || typeof child === "number"
        ? createTextElement(child)
        : child
    )
  };
}

export function renderToDOM(vnode) {
  if (vnode == null || typeof vnode === "boolean") {
    return document.createTextNode("");
  }

  if (typeof vnode === "string" || typeof vnode === "number") {
    return document.createTextNode(String(vnode));
  }

  if (vnode.type === "TEXT_ELEMENT") {
    return document.createTextNode(vnode.props.nodeValue); // Strictly safe text node
  }

  const element = document.createElement(vnode.type);
  // ...
  for (const child of vnode.children || []) {
    element.appendChild(renderToDOM(child));
  }
  return element;
}

## 4. Defect 2: Input Focus Loss & Caret Desynchronization on Reactive Re-renders

### 4.1. Defect Description
In Exercise 2 (`app.js`), typing into the task input field (`<input onInput={event => setInput(event.target.value)} />`) dispatches a state update via `useState`. In the AI initial implementation:
- Calling `setInput(...)` invoked `renderApp()`.
- `renderApp()` executed `rootElement.replaceChildren(dom)`, which destroyed the entire DOM subtree and remounted brand-new DOM nodes.
- **The Defect:** Every keystroke caused the active input element to detach from the DOM. `document.activeElement` instantly reverted to `document.body`. The user experienced focus loss (`blur`) after typing a single character, requiring a click on the input box for each character. Furthermore, cursor caret positions (`selectionStart`, `selectionEnd`) were wiped.

### 4.2. Diagnostic Method
1. **DevTools Breakpoint & Active Element Tracking**:
   - In Chrome DevTools, configured an **Event Listener Breakpoint** on `input`.
   - In the DevTools Console, inspected `document.activeElement`:
     ```javascript
     document.activeElement // Before render: <input type="text">
     // Step over renderApp execution:
     document.activeElement // Reverted to <body>. Focus destroyed!
     ```
2. **User Experience Verification**:
   - Attempted typing "Review PR". After pressing 'R', the input lost focus immediately. No further characters could be typed without clicking the input box again.

### 4.3. Refactored Solution (Verified Clean Engineering Fix)

#### Defective Code (AI-Generated):
```javascript
// DEFECTIVE: Wipes DOM without preserving active element or caret positions
export function renderApp() {
  stateCursor = 0;
  const vnode = rootComponent();
  const dom = renderToDOM(vnode);
  rootElement.replaceChildren(dom); // Focus and caret permanently lost
}
```

#### Refactored Code (Verified Fix in `mini_react.js`):
```javascript
// VERIFIED: Preserves activeElement, vnodeId, and cursor selection range
export function renderApp() {
  if (!rootElement || !rootComponent) return;

  // 1. Snapshot active focus and cursor caret positions
  const active = document.activeElement;
  const oldId = active?.dataset?.vnodeId;
  const start = active?.selectionStart;
  const end = active?.selectionEnd;

  stateCursor = 0;
  nodeId = 0;
  eventRegistry = new Map();

  // 2. Re-render virtual tree and mount to DOM
  const vnode = rootComponent();
  const dom = renderToDOM(vnode);

  rootElement.replaceChildren(dom);

  // 3. Restore focus and cursor selection seamlessly
  if (oldId) {
    const replacement = rootElement.querySelector(
      `[data-vnode-id="${oldId}"]`
    );

    if (replacement) {
      replacement.focus();

      if (
        typeof start === "number" &&
        typeof end === "number" &&
        typeof replacement.setSelectionRange === "function"
      ) {
        replacement.setSelectionRange(start, end);
      }
    }
  }
}
```
**Verification Outcome:** Typing long strings into the task input operates smoothly at 60 FPS without losing focus or resetting the cursor caret.

## 5. Defect 3: State Cursor Pointer Drift & Index Desynchronization in Custom `useState`

### 5.1. Defect Description
In Exercise 2, the React hook architecture is simulated via a sequential state array (`stateStore = []`) and an index cursor (`stateCursor = 0`). In the code initially generated by the AI:
- `stateCursor` was incremented during each `useState(initialValue)` invocation.
- **The Defect:** The AI omitted resetting `stateCursor = 0` at the beginning of each render cycle in `renderApp()`.
- On the first render, `TaskApp` called `useState` 3 times (`tasks` at index 0, `filter` at index 1, `input` at index 2), leaving `stateCursor = 3`.
- When the user added a task or toggled a checkbox, `renderApp()` re-ran `TaskApp()`. Because `stateCursor` remained at 3, the second render registered `tasks` at index 3, `filter` at index 4, and `input` at index 5.
- **Consequences:**
  1. `stateStore` grew infinitely on every interaction (`[0..2]`, `[3..5]`, `[6..8]`).
  2. The application lost reference to previously updated state values, resetting tasks to their initial state or crashing with `undefined`.
  3. The AI initial `setState` implementation only accepted static values (`stateStore[currentIndex] = nextValue`) rather than supporting functional updaters (`setState(previous => ...)`), causing stale closure bugs during concurrent state transitions.

### 5.2. Diagnostic Method
1. **Console Telemetry & State Array Inspection**:
   In Chrome DevTools Console, logged `stateCursor` and `stateStore`:
   ```javascript
   console.log("Cursor before render:", stateCursor);
   console.log("stateStore snapshot:", [...stateStore]);
   ```
   - Before fix: After 3 task updates, `stateStore` contained 9 elements instead of 3, and `stateCursor` was 9.
   - After fix: `stateCursor` consistently resets to 0 before each render and terminates at 3.
2. **Git Diff Inspection (`git diff 3cb5741 25f33b7`)**:
   Verified the introduction of `stateCursor = 0` inside `renderApp()` and functional update closure support inside `setState`.

### 5.3. Refactored Solution (Verified Clean Engineering Fix)

#### Defective Code (AI-Generated):
```javascript
// DEFECTIVE: Unbounded cursor growth and naive setter
let stateStore = [];
let stateCursor = 0;

export function useState(initialValue) {
  const currentIndex = stateCursor;
  if (stateStore[currentIndex] === undefined) {
    stateStore[currentIndex] = initialValue;
  }
  function setState(nextValue) {
    stateStore[currentIndex] = nextValue; // Stale closure and no functional updater
    renderApp();
  }
  stateCursor++;
  return [stateStore[currentIndex], setState];
}

export function renderApp() {
  // Missing stateCursor = 0. Cursor drifts indefinitely
  const dom = renderToDOM(rootComponent());
  rootElement.replaceChildren(dom);
}
```

#### Refactored Code (Verified Fix in `mini_react.js`):
```javascript
// VERIFIED: Deterministic Cursor Reset and Functional Update Dispatcher
const stateStore = [];
let stateCursor = 0;

export function useState(initialValue) {
  const currentIndex = stateCursor;

  if (!(currentIndex in stateStore)) {
    stateStore[currentIndex] =
      typeof initialValue === "function"
        ? initialValue()
        : initialValue;
  }

  function setState(nextValue) {
    // Supports functional updates: setState(prev => ...)
    stateStore[currentIndex] =
      typeof nextValue === "function"
        ? nextValue(stateStore[currentIndex])
        : nextValue;

    renderApp();
  }

  stateCursor++;

  return [stateStore[currentIndex], setState];
}

export function renderApp() {
  if (!rootElement || !rootComponent) return;

  // Crucial: Reset cursor to 0 before every render pass
  stateCursor = 0;
  nodeId = 0;
  eventRegistry = new Map();

  const vnode = rootComponent();
  const dom = renderToDOM(vnode);
  rootElement.replaceChildren(dom);
  // ...
}
```
**Verification Outcome:** Adding, completing, filtering, and deleting tasks updates `stateStore` deterministically at indices 0 (`tasks`), 1 (`filter`), and 2 (`input`). No memory leak or cursor drift occurs across repeated interactions.

## 6. Architectural Hardening: Root Event Delegation

In addition to the 3 primary defects, the AI originally attached event listeners directly to individual DOM nodes inside `renderToDOM`:
- **Problem:** Because `renderApp()` destroys and recreates the DOM on every state update, binding `addEventListener` to every button and input element leads to event listener thrashing and memory leaks.
- **Engineering Fix (`installDelegation`)**:
  Implemented the **Root Event Delegation** pattern. A single listener is attached to `rootElement` for `click`, `input`, `change`, and `submit`. When an event bubbles up, the target element is inspected using `dataset.vnodeId` and matched against the centralized `eventRegistry` Map:
  ```javascript
  rootElement.addEventListener(eventType, event => {
    let target = event.target;
    while (target && target !== rootElement) {
      const id = target.dataset?.vnodeId;
      const handler = id ? eventRegistry.get(id)?.[eventType] : null;
      if (handler) {
        handler(event);
        return;
      }
      target = target.parentElement;
    }
  });
  ```

### 7.2. Core Oral Defense Questions and Answers

#### Question 1: "Why must `useState` reset `stateCursor = 0` before each re-render pass inside `renderApp()`?"
> **Answer:** In Mini React, `useState` operates via an index cursor into a sequential flat array (`stateStore`). When the component executes, each invocation of `useState` retrieves the value at `stateStore[stateCursor]` and increments `stateCursor++`.
> If `stateCursor` is not reset to `0` at the start of `renderApp()`, the subsequent render will read from out-of-bounds indices (for example, indices 3, 4, 5 instead of 0, 1, 2). This causes state desynchronization, array memory bloat, and complete loss of previously persisted state.

#### Question 2: "Explain the mechanism used to resolve Input Focus Loss and Caret Jump during typing in Mini React."
> **Answer:** Due to the simple architecture of Mini React using `rootElement.replaceChildren(dom)` on every state transition, the active `<input>` element is detached from the DOM tree, causing the browser to reset focus to `document.body`.
> To prevent this, `renderApp()` captures a snapshot before unmounting: `oldId = active?.dataset?.vnodeId`, as well as `selectionStart` and `selectionEnd`. After the new DOM tree is mounted, the engine queries the newly created node using `querySelector([data-vnode-id="${oldId}"])`, calls `.focus()`, and restores the caret position using `.setSelectionRange(start, end)`.

#### Question 3: "How does Root Event Delegation in `installDelegation()` work, and what benefits does it provide?"
> **Answer:** Instead of attaching individual event listeners to every descendant `<button>` or `<input>` (which causes high memory overhead and listener leaks upon DOM replacement), a single event listener is attached to `rootElement` for `click`, `input`, `change`, and `submit`.
> When an event bubbles up, the dispatcher traverses up the tree using `while (target && target !== rootElement)`, extracts `data-vnode-id`, retrieves the associated callback from `eventRegistry.get(id)`, and executes it. This eliminates memory leaks and provides stable event dispatching.

#### Question 4: "How does your Mini React implementation mitigate Cross-Site Scripting (XSS) vulnerabilities?"
> **Answer:** In `mini_react.js`, `createElement` normalizes all child strings and numbers into `TEXT_ELEMENT` objects. During DOM rendering in `renderToDOM()`, these nodes are strictly constructed using `document.createTextNode(vnode.props.nodeValue)` rather than `innerHTML`.
> This guarantees that the browser parses text content as inert character data, neutralizing any malicious script payloads such as `<script>alert(1)</script>` or `<img onerror=...>`, as verified by the automated assertions in `test_runner.js`.

#### Question 5: "Why should state updates in `addTask` and `toggleTask` use the functional updater pattern `setTasks(previous => ...)` instead of referencing the outer `tasks` variable directly?"
> **Answer:** When multiple state updates occur rapidly or inside asynchronous closures, the outer variable `tasks` in the render scope may represent a stale closure value. Using the functional updater form `previous => ...` guarantees that `setState` passes the most up-to-date state value stored in `stateStore[currentIndex]`, preventing accidental state overwrites and dropped updates.
